# 仕様駆動開発の変更管理手順（提案）

## 基本原則

`docs/spec/`をAIエージェントと開発者が共通に参照する変更契約とする。**as-is**（観測できる現行実装）と**to-be**（合意した期待仕様）を混同しない。仕様の採用前には`Proposed`、合意後は`Accepted`、実装後は`Implemented`、検証証拠があって初めて`Verified`とする。

## ワークフロー

1. **Issue:** `Summary / Expected behavior / Actual behavior / Evidence / Impact / Priority / Acceptance criteria`を記載し、重複を確認する。
2. **Spec:** 入出力、失敗時挙動、モデル・座標系、通常/高速・動画/画像・ズーム状態の対象範囲を明示する。CLI・環境変数・JSON互換性に影響する場合は特記する。
3. **Acceptance tests:** 意味のある仕様ごとに再現例を設計する。mock/CPUテストとGPU/ゲート公開モデルによる統合テストを明確に分ける。
4. **Implementation:** 合意した契約に従いコードを変更する。AI生成コードも未実行テストを成功扱いしない。
5. **Review:** コード、README、仕様書、モデル・ライセンス依存、例外系、実行速度とスコアの比較可能性を確認し、[仕様・実装・検証対応表](verification_matrix_ja.md)の該当IDを更新する。
6. **Merge:** 仕様とテストの対応を確認し、未検証部分は`Known issue`としてIssueに残す。

## テストの分類

- **静的:** Python構文、Markdownの相対リンク、CLIと設定ドキュメントの整合。
- **単体／mock:** 各モデル不在時の振る舞い、対象人物の選択、姿勢描画とスコア境界、出力エラー処理。
- **実モデル／実映像:** MPS/CUDA/CPU対応、足先推定、複数人・遮蔽、時間的な安定性、パフォーマンス。
- **比較:** 同じ入力映像・フレーム・重み・条件で測定し、モデルバージョンと環境を記録する。

## PRの必須項目

- 関連Issue、変更した仕様箇所、ユーザー可視の差分
- 受入条件と実行したテストコマンド・環境・結果
- **実施していない検証**、既知の問題、後続Issue
- モデル/角度/スコアの互換性、ドキュメントの更新範囲

## 運用上の注意

既存仕様とコードが食い違う場合、どちらかを無条件に正とせず、Issueで現行動作と期待仕様を分けて合意する。AIエージェントはモデルの推論品質・実動画での再現性・外部パッケージの互換性を、コードを読んだだけで検証済みと判定しない。`docs/spec/`は意思決定の基盤であり、ソースコードの自動同期機能ではない。軽量なリンク・構文検査と、CPU/mock回帰テスト、GPU実機試験の到達範囲を区別してレビューする。

この手順は当初提案であり、チームによる承認後に規範として運用する。
